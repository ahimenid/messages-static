# Статика: список сообщений

Три файла (`index.html`, `styles.css`, `app.js`) + `mock.json` для превью. Никаких зависимостей и сборки — заливаются как есть в Object Storage с website hosting.

## Настройка

В начале `app.js`:

- `API_BASE` — URL API Gateway перед Cloud Function
- `YANDEX_CLIENT_ID` — client_id приложения Яндекс ID
- `PAGE_SIZE` (100), `WINDOW_HOURS` (72) — первая страница
- `POLL_DESKTOP_MS` (7 с), `POLL_MOBILE_MS` (60 с)

В приложении Яндекс ID указать Redirect URI = URL самой страницы (`https://<bucket>.website.yandexcloud.net/index.html`).

Телефон определяется по `pointer: coarse`, а не по ширине окна. Опрос останавливается, пока вкладка скрыта, и делает одно обновление сразу при возврате.

## Раскладка бакета

```
public/{room}/{YYYY-MM-DD}/{ISO8601}-{level}-{guid}.json   сообщения
public/{room}/resolved/{guid}.json                          отметки «решено»
config/rooms.json                                           имена и порядок комнат (правится руками)
settings/users/{uid}.json                                   настройки пользователя
settings/rooms/{room}.json                                  умолчания комнаты, переопределяют общие
private/...                                                 зарезервировано
```

Сутки в ключе нужны потому, что `ListObjectsV2` отдаёт ключи только по возрастанию: бэкенд берёт список дней (`delimiter=/`), идёт от свежего к старому и останавливается, набрав `limit`. Уровень в имени ключа позволяет фильтровать по листингу, не скачивая тела: `GetObject` вызывается только для тех сообщений, которые реально уходят в ответ.

Решение инцидента — отдельный объект `public/{room}/resolved/{guid}.json`, исходное сообщение никогда не переписывается. Один листинг этого префикса даёт множество решённых id; событие-решение в ленте не показывается, а помечает исходное зелёной рамкой и галочкой.

Сообщение (тело объекта):

```json
{
  "id": "b2d9a610-77c5-4a08-9b3f-2c1e5d7a0022",
  "timestamp": "2026-09-07T03:41:55Z",
  "source": "disk-watch",
  "level": "trace | debug | info | warning | error | critical",
  "text": "На /var осталось 2% свободного места."
}
```

`id` — guid, генерируется сервисом-отправителем и дублируется в имени ключа. Сообщение без уровня считается `info`.

## Настройки пользователя

`settings/users/{uid}.json`, создаётся автоматически при первом входе:

```json
{
  "defaults": { "min_level": "info", "unresolved_only": false },
  "rooms": { "jobs": { "min_level": "warning", "unresolved_only": true } },
  "last_room": "infra"
}
```

Порядок применения: `settings/rooms/{room}.json` задаёт умолчания комнаты поверх общих, файл пользователя переопределяет и то и другое. Порог и фильтр «только нерешённые» хранятся на каждую комнату отдельно.

## Что должен отдавать бэкенд

Cookie сессии — `HttpOnly; Secure; SameSite=None` (фронт и API на разных доменах), и на API Gateway нужен CORS с `Access-Control-Allow-Credentials: true` и конкретным `Access-Control-Allow-Origin`.

- `POST /auth` — тело `{"token": "<OAuth-токен>"}`. Валидирует через `login.yandex.ru/info`, сверяет uid с whitelist. `200 {"login": "..."}` + Set-Cookie, `403` если uid не в списке. Здесь же создаётся файл настроек, если его нет.
- `GET /auth/me` — `200 {"login": "..."}` при живой сессии, иначе `401`.
- `POST /auth/logout` — гасит cookie.
- `GET /rooms` — `200 {"rooms": [{"id": "infra", "title": "Инфраструктура"}], "settings": {...}}`. Список комнат — объединение префиксов, реально существующих в `public/`, и записей `config/rooms.json` (оттуда берутся имена и порядок).
- `PUT /settings` — тело целиком как в файле пользователя, пишется в `settings/users/{uid}.json`.
- `GET /messages` — параметры:

| параметр | смысл |
| --- | --- |
| `room` | id комнаты |
| `min_level` | минимальный уровень, включительно |
| `limit` | сколько сообщений отдать (100) |
| `unresolved` | `1` — считать `limit` по нерешённым |
| `window_hours` | первая страница: не старше N часов, но не больше `limit` |
| `after` | ключ последнего известного сообщения — опрос новых |
| `before` | ключ самого старого показанного — «Показать ещё» |

Ответ `200 {"messages": [...], "resolved": ["guid", ...], "has_more": true}`, `401` при истёкшей сессии.

- `window_hours` и `limit` работают как «или»: за 72 часа отдаём всё, что есть, но не больше 100; добирать до 100 сообщениями недельной давности не нужно.
- «Показать ещё» — следующие 100 без ограничения по дате, `has_more: false` когда комната кончилась.
- При `unresolved=1` бэкенд листает дальше, пока не наберёт 100 именно нерешённых.
- `resolved` — id, ставшие решёнными; для запроса с `after` достаточно отметок, появившихся после предыдущего опроса.
- На запрос с `after` полезно отдавать `ETag`: фронт присылает `If-None-Match` и на `304` не тратит трафик. ETag достаточно считать от самого свежего ключа и числа отметок «решено».

## Превью без бэкенда

`index.html?mock=1` — авторизация пропускается, комнаты, настройки и сообщения берутся из `mock.json`, фильтры отрабатывают на клиенте.
